# Product and feature pages

**Master decision:** show or tell. Can a demo, a workflow or a single screenshot carry the page, or does it need capability blocks?

## Section order

1. `hero`: the feature's promise in outcome terms + the product UI for that feature
2. `problem`: how the job is done today and what it costs (time, errors, risk)
3. `features`: 3–4 capability blocks
4. `demo`: a short muted looping video (≤ 15s), an interactive walkthrough, or step-through screenshots
5. `proof`: a case study or quote about *this* feature
6. `integrations`: tools this feature connects to
7. `related`: 2–3 links to neighbouring features
8. `cta-band`

## Show vs tell

| Feature is… | Lead with | Component |
|---|---|---|
| Visual (dashboards, editors, builders) | Large screenshot or video | `features/alternating` rows, each with a UI crop |
| A process across steps | Workflow narrative: intake → plan → act → report | Linear's four-section workflow; `features/numbered-triplet` |
| Best understood by trying | A working demo next to the copy | `features/workbench` |
| Technical (API, SDK) | A code sample with a copy button, plus the result | Workbench with a code panel |
| A replacement for spreadsheets or email | Before / with comparison | `features/compare` |

## Rules

- Each capability block: a title that states the benefit, 2–3 lines of body, one UI crop, and an optional "Learn more" link.
- Alternate image sides between rows; keep the copy column width the same.
- Crop screenshots to the part that matters and add a short caption. Don't show a whole dashboard at 30% scale.
- Videos: muted, `playsinline`, with visible controls or a pause button, a poster image, and no sound by default.
